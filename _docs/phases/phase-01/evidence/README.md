**Important limits.**

- There is still no automated test target. E01–E08 are Swift harnesses kept in this folder and compiled together with the app's own source files; the build command is at the top of each `main.swift` (E04: `run.sh`). E09 is a shell harness that runs the actual scripts in `Tools/` with stub commands; its usage is at the top of `E09/run.sh`. Temporary output went to a temporary folder outside the project.
- The executor has no screen recording or accessibility access: the real window was not seen. E03 renders rows with `ImageRenderer`; the PDFKit view of the grid blocks cannot be drawn that way, so the grid, the order numbers, the toolbar, the dialogs and drag and drop are practical checks ([validation plan](../../../../_specs/getting-started/validation.md), items 12–15). E05 and E06 build the real window content in an off-screen window; its rendering of the preview column is not representative (drawn white), so it only measures sizes and samples the divider pixels.
- Every reorder re-assigns the priorities of all of the user's waiting jobs on that printer (JOB-001 rule 4). While the user had own jobs in the queue (15 paused jobs for most of the session), no move was applied to cupsd: E01 covers the logic and E04 computes, without applying, whether a move is possible. When the user's queue had become empty, E07 applied the moves to cupsd with held test jobs only, after checking that the queue held no other job. Pausing pending jobs was not run (a pending job with a document would print).
- No check printed on paper. Test jobs were held (`lp -H hold`) or empty (`Create-Job` without a document), titled `MPQV E04 …`, and removed afterwards, including from the completed-job history. A snapshot of the user's queued jobs (job ID, state, priority) was identical before and after each run.
